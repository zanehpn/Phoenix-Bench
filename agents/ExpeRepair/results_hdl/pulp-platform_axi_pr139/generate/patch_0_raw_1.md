### Phase 1: FIX ANALYSIS

1. **Problem summary**

`tb_axi_lite_regs` has a race between:
- the **directed sanity check** (write known value, read it back, assert exact match), and
- the **random `reg_load` stimulus** generated by `toggle_load()`.

For some seeds, random load updates the same register bytes before/during the directed readback, so the read data is no longer `64'hDEADBEEFDEADBEEF` (example got `de01beef`), causing non-deterministic assertion failures.

2. **Where it occurs**

In `test/tb_axi_lite_regs.sv`:
- `proc_generate_direct_load` starts `toggle_load()` threads immediately.
- `toggle_load()` starts random load activity shortly after reset and runs forever.
- Meanwhile, `proc_generate_axi_traffic` performs the directed write/read check assuming register content is stable.

So the collision is between:
- `proc_generate_axi_traffic` (directed check), and
- `toggle_load()` (random load pulses on `reg_load`/`reg_d`).

3. **Best practices for fix**

- Keep directed smoke checks deterministic.
- Start random background stimuli only after deterministic checks complete.
- Make minimal changes; preserve existing random behavior for the rest of the test.
- Avoid timing hacks; use explicit synchronization (enable flag/event).

4. **Fix approach**

Introduce a synchronization flag (e.g. `rand_load_enable`):
- initialize it to `0`,
- set it to `1` only after directed write/read assertions complete,
- in each `toggle_load()` task, wait for this flag before entering random forever loop.

This prevents random load from corrupting the known-value readback while keeping existing random stress after that point.

<original>  task automatic toggle_load(int unsigned byte_i);
    byte_t       rand_val;
    int unsigned rand_wait;

      reg_load[byte_i] &lt;= #ApplTime 1'b1;
      @(posedge clk);

    end
