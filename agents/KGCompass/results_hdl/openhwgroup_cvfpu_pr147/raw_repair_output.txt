The bug is in `src/fpnew_cast_multi.sv`, in the integer-input normalization path:

```systemverilog
assign int_sign     = int_value[INT_MAN_WIDTH-1] & ~op_mod_q;
assign int_mantissa = int_sign ? unsigned'(-int_value) : int_value;
```

For `fcvt.w.d` from a negative double to a signed integer, this code computes the magnitude correctly, but later the sign is re-applied incorrectly via a positive unsigned result path, yielding `0x0000000080000000` instead of the properly sign-extended `0xffffffff80000000`.

The statement you asked about:

```systemverilog
assign rounded_int_res = rounded_sign ? unsigned'(-rounded_abs) : rounded_abs;
```

is meant to reconstruct the signed integer from the rounded absolute value:
- if `rounded_sign == 1`, negate the absolute value to produce the signed negative integer,
- otherwise keep it positive.

The issue is that the result is being cast to `unsigned`, which can suppress proper signed interpretation / sign extension in downstream handling for integer results.

## Fix

We should ensure the signed integer result is produced as a signed value before being packed into the output, so negative results are sign-extended correctly.
