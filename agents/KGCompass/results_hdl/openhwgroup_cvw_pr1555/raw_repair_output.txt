The bug is in the tracer’s CSR-change detection macro in `testbench/common/wallyTracer.sv`.

### Why this is the likely source
`CONNECT_CSR` currently does two problematic things:

1. It declares `prev_csr_*` without reset/initialization, so the first observed value can be X/old state.
2. It continuously assigns the CSR trace value from `valid ? val : prev_csr_*`, which can cause the tracer to briefly observe stale or unintended CSR values during stalls/flushes.
3. It also uses `rvvi.csr[...]` on both sides of the assignment chain in a way that can create ordering/race issues in simulation, which is consistent with spurious `mip.MTIP` transitions.

A safer approach is to register the previous value with reset and drive the trace CSR from the current `val` only when valid, while detecting change against the registered previous value.
